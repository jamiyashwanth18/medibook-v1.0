<!-- sdlc:auto:start overview -->
MediBook V1 is a healthcare appointment management application generated by the Quorq AI SDLC platform, split into two independently runnable apps in one repository. The `frontend/` is a Vite + React 19 single-page app whose screens were already approved and currently render seeded sample data rather than calling a real API. The `backend/` is a FastAPI 0.115 service scaffolded from no approved architecture yet, so it only exposes a `/health` liveness check and the SQLAlchemy/Pydantic plumbing (database session, Base model, stub response schema, empty routers package) needed to add real endpoints later. The backend defaults to a local SQLite file so it runs without any database server, while `docker-compose.yml` can stand up a PostgreSQL 16 container for the approved Postgres/AWS stack.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository.
2. Backend: cd backend && pip install -r requirements.txt
3. (Optional) Start a Postgres database: from the repo root run `docker-compose up -d db`, then set DATABASE_URL to point at it before starting the backend (it defaults to a local sqlite:///./app.db file otherwise).
4. Run the backend: uvicorn app.main:app --reload (from backend/, serves on http://localhost:8000; tables are created automatically on startup from the SQLAlchemy models).
5. Frontend: cd frontend && npm install
6. Run the frontend: npm run dev (Vite dev server on http://localhost:5173, which backend CORS allows by default).
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend routers are generated one per architecture component that owns endpoints, registered under app/routers/ (currently empty, to be filled in as the architecture is approved).
- Every generated backend route returns a typed StubResponse (endpoint, status, detail) until implemented, keeping the service startable with a complete OpenAPI document.
- SQLAlchemy models all inherit the shared Base from app/database.py; app/main.py imports app.models before calling Base.metadata.create_all so new tables register automatically on startup.
- Backend session access goes through the get_db() FastAPI dependency, which yields one Session per request and always closes it.
- Backend environment is configuration-driven: DATABASE_URL selects the database (SQLite by default) and ALLOWED_ORIGINS (comma-separated) configures CORS, defaulting to the local Vite dev origins.
- Frontend API calls go through the single apiFetch() helper in src/lib/api.ts, which attaches a bearer token (session token if set, else the baked-in API secret) and resolves against API_BASE_URL (overridable via VITE_API_BASE_URL).
- Frontend screens currently render seeded/sample data rather than calling the backend; src/lib/api.ts is the intended integration seam for wiring a screen to a real endpoint.
- Frontend and backend each keep their own lint/format/test tooling (ESLint+Prettier+Vitest vs. ruff+pytest) with config files at each app's root.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend requests to the backend are blocked by CORS. | Ensure the backend's ALLOWED_ORIGINS env var includes the frontend's origin, or run the frontend on the default dev origins (http://localhost:5173 / http://127.0.0.1:5173), which app/main.py allows out of the box. |
| `pytest` fails with `ModuleNotFoundError: No module named 'app'` when run from an unexpected location. | Run pytest from the backend/ directory so backend/pytest.ini's `pythonpath = .` setting puts the app package on sys.path. |
| `npm run test:e2e` fails to start the backend. | playwright.config.ts expects a Python virtualenv at backend/.venv with dependencies installed; create it and `pip install -r requirements.txt` into backend/.venv before running the e2e suite, or set E2E_BASE_URL to point at an already-running deployment instead. |
| `npm run build` succeeds but the app doesn't actually type-check. | Run `npm run typecheck` (tsc --noEmit) separately, since `vite build` does not type-check and can tree-shake out type errors in unused modules like src/lib/api.ts. |
| Backend data disappears between restarts or you want to use the approved Postgres stack. | The backend defaults to a local sqlite:///./app.db file with no migrations; start the Postgres container with `docker-compose up -d db` and set DATABASE_URL to point at it before starting uvicorn. |
<!-- sdlc:auto:end troubleshooting -->
