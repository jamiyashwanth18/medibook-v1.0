<!-- sdlc:auto:start overview -->
MediBook V1 is a healthcare appointment management system generated by the Quorq AI SDLC platform, split into two independently runnable apps in one repo. The frontend is a Vite + React 19 single-page app whose screens (find a doctor, appointments, doctor schedule/availability, admin console) were generated from an approved design and currently run on seeded sample data behind a role-based login (patient/doctor/admin). The backend is a FastAPI 0.115 service with SQLAlchemy models and Alembic migrations, defaulting to a local SQLite database (swappable to Postgres via DATABASE_URL); most of its routes are typed stubs from the approved API spec, with authentication (register/login/logout/me), specialization and doctor admin management, doctor self-availability, and audit-log listing actually implemented.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start setup -->
1. Clone the repository.
2. Backend: cd backend && pip install -r requirements.txt
3. Backend: start the API with uvicorn (see run_commands) -- it runs Alembic migrations and creates the local SQLite database automatically on startup.
4. Frontend: cd frontend && npm install
5. Frontend: start the dev server with npm run dev (see run_commands); it talks to the backend at http://localhost:8000 by default (VITE_API_BASE_URL overrides this).
6. Optional: docker compose up -d to run a Postgres 16 database instead of SQLite, then point the backend's DATABASE_URL at it.
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend routes are organized one router per architecture component (app/routers/api.py) with one handler per endpoint declared in the approved API spec; unimplemented endpoints return a typed StubResponse(endpoint=..., status="not_implemented") rather than erroring, keeping the OpenAPI document complete.
- SQLAlchemy models (app/models.py) use UUID primary keys (SQLAlchemy Uuid type) and timezone-aware DateTime columns, with one model per entity in the approved data model and no business logic embedded in the ORM layer.
- Pydantic schemas (app/schemas.py) follow a Request/Response pair per entity, with field validators normalizing email/phone and enforcing password strength (>=8 chars, letter + digit).
- Role and status values are centralized as string constants in app/models.py (ROLE_ADMIN/ROLE_DOCTOR/ROLE_PATIENT, APPOINTMENT_STATUSES) rather than enums scattered across handlers.
- Schema changes are made only via a new Alembic revision under backend/alembic/versions; the app runs migrations to head automatically on startup.
- The database defaults to local SQLite with no setup required; pointing DATABASE_URL at Postgres changes nothing else in the code.
- Frontend screens live one-per-file under src/screens/, built against a shared component/icon vocabulary (src/lib/ui.tsx, src/lib/icons.tsx) and a single brand token source (src/lib/brand.ts, src/index.css).
- All frontend API calls go through the single apiFetch helper in src/lib/api.ts, which attaches a bearer token (session token if logged in, else a shared secret) and centralizes 401 handling.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| `pytest` fails with `ModuleNotFoundError: No module named 'app'`. | Run pytest from the backend/ directory; pytest.ini sets pythonpath = . relative to that directory. |
| Frontend screens can't reach the backend / CORS errors in the browser console. | The backend's allowed CORS origins come from its settings (allowed_origins); ensure the backend is configured to allow the frontend's dev origin (e.g. the Vite dev server URL), and that VITE_API_BASE_URL points at the running backend (defaults to http://localhost:8000). |
| `npm run build` succeeds but the app is actually broken (type errors). | `npm run build` does not typecheck; run `npm run typecheck` separately to catch TypeScript errors before relying on the build. |
| `npm run test:e2e` hangs or fails to start services. | Without E2E_BASE_URL set, Playwright boots the backend from `backend/.venv` and builds/previews the frontend itself -- ensure backend dependencies are installed into backend/.venv first, or set E2E_BASE_URL to an already-running deployment. |
| Backend won't start against a real database. | Set DATABASE_URL to the Postgres connection string (e.g. matching the docker-compose db service); the app runs Alembic migrations to head automatically on startup, so no manual migration step is needed. |
<!-- sdlc:auto:end troubleshooting -->
